# ClaimOps

A multi-tenant claims operations platform with a real backend: a real
XGBoost fraud model, a real SQLite database, a real intake pipeline, and a
real (TF-IDF) document retrieval system — built as a portfolio project
while applying to Forward Deployed Engineer roles at claims-tech companies.

This is the second pass on this project. The first pass was a frontend that
computed everything client-side against hardcoded arrays — nothing
persisted, nothing was server-processed. That version was rebuilt from the
ground up into what's described below after review caught it for what it
was. `docs/02-architecture-decisions.md` has the full, unflattering history
if you want it — this README describes what actually exists today.

## What's actually real here (verified, not just written)

- **A real XGBoost model.** Trained with the real `xgboost` Python library
  (60 trees, depth 3) on synthetic data with a nonlinear interaction term a
  linear model can't fit. Exported as JSON trees and run with a pure-TypeScript
  tree-traversal engine (no native binary needed at runtime) — verified to
  match Python's own `booster.predict()` output to 8 decimal places on held-out
  rows. See `src/lib/fraud-model.ts` for the full explanation, including a
  real bug (XGBoost's `base_score` intercept) that was caught and fixed
  during that verification, not assumed away.
- **A real database.** SQLite, actual file on disk at `data/claimops.db`.
  Approve a claim, refresh the page, restart the dev server entirely — the
  status holds. Verified via direct API testing, not just "should work."
- **A real intake pipeline.** `POST /api/claims` (and its CSV/webhook
  variants) runs a claim through fraud scoring → coverage retrieval → rules
  engine → smart assignment, server-side, writing a genuine audit trail to
  the database at every step.
- **Real retrieval for the coverage assistant.** Upload a PDF policy
  document at `/documents`, and it's actually parsed (pdf-parse), chunked,
  and indexed with TF-IDF. Claims for that tenant are matched against the
  real uploaded text via cosine similarity — verified end-to-end with a
  real generated PDF during testing, not a lookup table keyed by claim type.
- **A real rules engine with a real builder UI.** Rules are rows in the
  `rules` table, created/edited/disabled/deleted at `/rules`, evaluated
  generically (not hardcoded per tenant) against every claim.
- **A real smart assignment engine.** Weighted scoring across skill,
  geography, license, seniority-vs-complexity, and current workload against
  an actual adjuster roster — not a random pick or a single if-statement.
- **Four real intake channels**, all normalizing into the same canonical
  schema and the same pipeline: a web form (`/adjuster/new`), a direct JSON
  API (`POST /api/claims`), bulk CSV (`POST /api/claims/csv`), and a public
  webhook endpoint (`POST /api/webhooks/claims`) that a real external
  system (or an email-to-webhook bridge like SendGrid Inbound Parse) could
  actually hit once this is deployed.
- **Two live tenants**, Acme Insurance and Voyage Travel Insurance, each
  with independent SLA targets, fraud thresholds, rules, and adjuster
  rosters, proving the multi-tenancy is structural rather than cosmetic.

## What's still a documented stand-in, and why

- **Coverage narrative generation.** The retrieval step is real (see above);
  turning retrieved passages into fluent prose is templated rather than
  generated by a hosted LLM, because a live LLM call needs a paid API key,
  which conflicts with running this at $0. This is the one piece where
  "real" stops at retrieval and doesn't extend to generation — see
  `src/lib/coverage-assistant.ts`.
- **SHAP attribution.** What's shown is the Saabas method (a real, published
  tree-attribution technique), not exact TreeSHAP, which needs a
  significantly more involved recursive algorithm to implement correctly.
  `scripts/train_xgb_fraud_model.py` also computes real SHAP values via the
  `shap` Python library at training time for comparison.
- **No auth.** Tenant switching is a dropdown, not a login. `users` table
  exists with roles but nothing enforces them yet.
- **GCP/Terraform** in `/infra` documents a target production architecture
  and is not deployed — deploying real cloud infrastructure needs an actual
  cloud account and billing, which is a decision for you to make, not
  something to fake.

## Important: SQLite works locally, not on Vercel

`npm run dev` (or any long-running Node process — a VPS, Railway, Render)
gets real, durable persistence from the SQLite file. **Vercel's serverless
functions have an ephemeral filesystem** — writes can vanish between
requests, so this will not reliably persist if deployed to Vercel as-is.
To deploy with real persistence there, migrate `src/lib/repo.ts`'s driver
from `better-sqlite3` to Postgres (Supabase free tier) using
`supabase/schema.sql`, which mirrors `src/lib/db/schema.sql`. This is a
contained swap (one file's internals), not a rewrite, because everything
else calls the repository functions, not the SQLite client directly.

## Running it

```bash
npm install
npm run db:seed   # populates data/claimops.db: 2 orgs, 6 rules, 7 adjusters,
                   # 1 sample policy document, 8 demo claims run through the
                   # real pipeline
npm run dev
```
Open http://localhost:3000. No environment variables or cloud accounts
required for local use.

To retrain the fraud model from scratch:
```bash
pip install xgboost shap numpy
python3 scripts/train_xgb_fraud_model.py
```

## Three ways to look at it

| Persona | Route | What it does |
|---|---|---|
| Implementation Engineer | `/onboarding` | Creates a real new tenant via `POST /api/organizations` |
| Claims Adjuster | `/adjuster`, `/adjuster/new`, `/adjuster/review` | Real queue, real FNOL submission, real human-review filtering |
| Rules admin | `/rules` | Real CRUD against the `rules` table |
| Documents | `/documents` | Real PDF upload, parsing, and indexing |
| Executive | `/executive` | Real aggregate KPIs computed from the database at request time |

## Stack

Next.js 16 (TypeScript, App Router) + Tailwind + Recharts. `better-sqlite3`
for local persistence, `pdf-parse` for real PDF text extraction (both
marked `serverExternalPackages` in `next.config.ts` — a real bundler
incompatibility with Turbopack was hit and fixed during development, see
that file's comments). XGBoost/scikit-learn/shap (Python) for offline model
training, exported to JSON and run in pure TypeScript at inference time.
